Fundamentos do PWA

Um Progressive Web App é um site que se comporta como aplicativo: instalável, rápido, confiável e capaz de funcionar sem internet.

O que é um PWA?

Um PWA é construído com tecnologias web comuns (HTML, CSS e JavaScript), mas adiciona três peças que mudam o jogo: HTTPS, um Web App Manifest e um Service Worker. Juntas, elas permitem instalar o site na tela inicial e usá-lo offline.

PWA × App nativo × Site tradicional

CritérioSite tradicionalPWAApp nativo
InstalávelNãoSim (sem loja)Sim (via loja)
Funciona offlineRaramenteSimSim
AtualizaçãoImediataAutomática, ao abrirDepende da loja/usuário
Base de códigoWebWeb (única para todas as plataformas)Uma por plataforma
Acesso a hardwareLimitadoBom e crescenteTotal
Peso de instalaçãoNenhumMuito baixoAlto

As três peças

  • HTTPSService Workers só funcionam em contexto seguro (exceção: localhost para desenvolvimento).
  • ManifestUm JSON que descreve nome, ícones, cores e modo de exibição do app.
  • Service WorkerUm script que fica entre a página e a rede e decide o que vem do cache.

Esqueleto mínimo de um PWA

<!-- 1) Liga o manifest -->
<link rel="manifest" href="manifest.webmanifest">

<script>
  // 2) Registra o Service Worker (só se o navegador suportar)
  if ('serviceWorker' in navigator) {
    navigator.serviceWorker.register('./sw.js');
  }
</script>

Módulo 2 de 5

Web App Manifest e Instalação

O manifest é o "RG" do seu app: diz ao navegador como ele se chama, que aparência tem e como deve abrir depois de instalado.

Propriedades essenciais

name / short_name
Nome completo (telas de instalação) e nome curto (abaixo do ícone na tela inicial).
start_url
URL aberta ao iniciar o app instalado. Use caminho relativo para funcionar em subpastas (GitHub Pages). Parâmetros como ?source=pwa ajudam a medir uso.
scope
Define quais URLs pertencem ao app. Links fora do escopo abrem no navegador comum.
display
standalone (sem barra do navegador, o mais comum), minimal-ui, fullscreen ou browser.
icons e purpose: "maskable"
Ícones any são exibidos como estão. Ícones maskable têm uma "zona segura" central (cerca de 80%) para o Android recortá-los em círculo, quadrado arredondado etc. sem cortar o desenho.
theme_color / background_color
Cor da barra de título do app e cor de fundo da tela de abertura.

Manifest do PWA Brasil (trecho)

{
  "name": "PWA Brasil (PT-BR)",
  "short_name": "PWA Brasil",
  "start_url": "./index.html?source=pwa", // onde o app instalado abre
  "scope": "./",                          // área controlada pelo app
  "display": "standalone",                // aparência de app nativo
  "icons": [
    { "src": "icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "icons/icon-maskable-512.png", "sizes": "512x512",
      "type": "image/png", "purpose": "maskable" } // recorte adaptativo
  ]
}

Observação: JSON puro não aceita comentários. Os comentários acima são apenas didáticos; o arquivo real não os contém.

Capturando o evento de instalação

let eventoInstalacao = null;

// O navegador dispara este evento quando o app É instalável.
window.addEventListener('beforeinstallprompt', (e) => {
  e.preventDefault();      // impede o mini-aviso automático
  eventoInstalacao = e;    // guarda para usar quando o usuário clicar
  botaoInstalar.disabled = false;
});

botaoInstalar.addEventListener('click', async () => {
  eventoInstalacao.prompt();                       // mostra o diálogo nativo
  const { outcome } = await eventoInstalacao.userChoice; // 'accepted' | 'dismissed'
});

Service Workers e Estratégias de Cache

O Service Worker é um proxy programável que roda em segundo plano, separado da página. É ele quem torna o app confiável offline.

Ciclo de vida

  1. register — a página pede o registro do sw.js.
  2. install — o SW é baixado e faz o pré-cache do App Shell.
  3. waiting — se já existe um SW ativo, o novo espera as abas antigas fecharem (ou skipWaiting).
  4. activate — assume o controle e limpa caches antigos.
  5. fetch — passa a interceptar cada requisição da página.
self.addEventListener('install', (e) => {
  // Baixa e guarda os arquivos essenciais
  e.waitUntil(caches.open('shell-v1').then((c) => c.addAll(['./', './app.js'])));
});

self.addEventListener('activate', (e) => {
  // Apaga caches de versões antigas
  e.waitUntil(limparCachesAntigos());
});

self.addEventListener('fetch', (e) => {
  // Decide: cache, rede, ou os dois?
  e.respondWith(caches.match(e.request).then((r) => r || fetch(e.request)));
});

Estratégias de cache

Cache First

Cache → (se faltar) rede. Mais rápida. Ideal para arquivos versionados: CSS, JS, imagens, fontes.

Network First

Rede → (se falhar) cache. Sempre fresca quando online. Ideal para HTML e dados que mudam.

Stale-While-Revalidate

Responde com o cache e atualiza em segundo plano. Equilíbrio entre velocidade e atualidade.

Módulo 4 de 5

Recursos Nativos e Engajamento

PWAs conversam com o sistema operacional: guardam dados, compartilham conteúdo e avisam o usuário.

Armazenamento local

  • localStorage: simples, síncrono, só texto (~5 MB). Este app guarda tema e progresso nele.
  • IndexedDB: banco assíncrono para dados estruturados e grandes.
  • CacheStorage: pares requisição/resposta, usado pelo Service Worker.
// Guardar e ler progresso do aluno
localStorage.setItem('progresso', JSON.stringify(['modulo-1']));
const feitos = JSON.parse(localStorage.getItem('progresso') || '[]');

Web Share API

if (navigator.share) {
  await navigator.share({
    title: 'PWA Brasil (PT-BR)',
    text: 'Aprenda a criar PWAs!',
    url: location.href
  });
}

Notificações

Exigem permissão do usuário, que deve ser pedida após um gesto (clique), nunca ao carregar a página. Para notificações com o app fechado é preciso a Push API e um servidor; aqui testamos notificações locais exibidas pelo Service Worker.

const permissao = await Notification.requestPermission(); // 'granted' | 'denied' | 'default'
if (permissao === 'granted') {
  const reg = await navigator.serviceWorker.ready;
  reg.showNotification('Olá!', { body: 'Notificação via Service Worker' });
}

Módulo 5 de 5

Auditoria, Ciclo de Atualização e Deploy

Um PWA de verdade precisa ser medido, atualizado com segurança e publicado em HTTPS.

Auditando com o Lighthouse

  1. Abra o app no Chrome e pressione F12 (DevTools).
  2. Vá à aba Lighthouse e marque Desempenho, Acessibilidade, Boas práticas e SEO.
  3. Clique em Analisar e leia as recomendações.
  4. Na aba Application, confira Manifest, Service Workers e Cache Storage.

Versões recentes do Lighthouse removeram a categoria "PWA" dedicada; os mesmos requisitos aparecem na aba Application e nas verificações de instalabilidade do DevTools.

Atualização de versão

Quando você altera o sw.js, o navegador baixa a nova versão, instala-a e a deixa em waiting. A página detecta isso e mostra o banner; ao clicar em "Atualizar", enviamos uma mensagem para o SW chamar skipWaiting(), e então recarregamos.

// --- app.js (página) ---
reg.addEventListener('updatefound', () => {
  const novo = reg.installing;
  novo.addEventListener('statechange', () => {
    // "installed" + já existe controller = há uma versão nova esperando
    if (novo.state === 'installed' && navigator.serviceWorker.controller) {
      mostrarBanner();
    }
  });
});
btnAtualizar.onclick = () => reg.waiting.postMessage({ tipo: 'PULAR_ESPERA' });
navigator.serviceWorker.addEventListener('controllerchange', () => location.reload());

// --- sw.js ---
self.addEventListener('message', (e) => {
  if (e.data.tipo === 'PULAR_ESPERA') self.skipWaiting();
});

Publicando no GitHub Pages (HTTPS grátis)

  1. Crie um repositório e envie todos os arquivos (index.html, sw.js, etc.) na raiz.
  2. Em Settings → Pages, escolha a branch main e a pasta / (root).
  3. Aguarde o deploy; o app ficará em https://usuario.github.io/repositorio/.
  4. Como todos os caminhos são relativos, o app funciona dentro da subpasta do repositório.

Para testar localmente: python3 -m http.server 8080 e abra http://localhost:8080. Abrir o arquivo com file:// não ativa o Service Worker.
